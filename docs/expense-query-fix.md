# Expense query compatibility fix

## Root cause and evidence

`queryExpenseMatches()` used `searchTerms array-contains <lookup>` as a mandatory candidate predicate for searches of three or more characters. A document without that field, with stale terms, or with terms generated by a different algorithm never reached the subsequent substring matcher. That matcher could not recover omitted candidates. Similarly, employee/project predicates required derived `employeeFilterKey`/`projectFilterKey` fields, making their later identity fallbacks ineffective.

There are incompatible writers: Next's `_creation.js` delegates to `expenseCreationService.js`, which atomically writes ISO `date`, numeric month/year, identity/filter fields, normalized prefix search terms and timestamps. In contrast, `functions/src/expense/lifecycle.js` contained its own search builder, overwriting terms during edits/reviews with lowercase whole values/whitespace tokens, without prefix, accent, punctuation or travel-field handling. Legacy direct creation remains allowed by `firestore.rules` and does not require the derived search/filter fields. Creation's current search builder itself includes Ayesha correctly; it should not be blamed for an omission without checking the stored document.

Both list modes also queried/ordered exclusively by `date`. Firestore omits documents missing that field before the JavaScript `date || expenseDate` fallback can run. Month/year or createdAt cannot repair this, nor should they replace an actual expense date.

These are verified source-level exclusion mechanisms. The production ₹531 document was not accessed, so its particular missing/stale field is not claimed as inspected. Regression fixtures reproduce the reported ₹1001 → ₹1532 result with a newest expense lacking derived indexes.

## Complete change

- `src/lib/server/expensePageService.js`: shared bounded scanner for normal and filtered pages; merges descending `date` and `expenseDate` queries, uses `date` as authoritative and the latter only when date is absent/empty; applies normalized substring and identity filters without unsafe derived-field query gates; returns canonical date to clients.
- `functions/src/expense/lifecycle.js`: replaces the divergent inline search builder with the existing Functions search-index module, matching creation semantics.
- `firestore.indexes.json`: adds employeeId ASC + expenseDate DESC collection index.
- `tests/expense-query-regression.test.mjs`: deterministic query-semantics tests and a real Firestore emulator integration test.
- This report.

No UI, amounts, totals formulas, creation payload, permission rules or monthly aggregate values are modified.

## Reads, security and pagination

Every query stays under `Companies/{authorized companyId}/Expenses` and inside the selected month/date range. Employee reads include employeeId equality in both streams and retain a final ownership check. Explicit conflicting companyId values are rejected.

Normal pages fetch batches of 31 per date stream; filtered pages fetch batches of 60. Each scanner invocation examines at most 300 candidates. Buffered reads can exceed examined candidates by up to one batch per stream. No request scans the unbounded expense collection. Employee first-page totals still require reading that employee's selected month, as before; owner/manager month totals still use the existing aggregate document.

Substring matching cannot safely use the current prefix-only, size-capped, optional searchTerms array. Selective filters may therefore require multiple bounded pages of the month. A future complete/versioned search index could optimize this, but switching back to the existing array would reintroduce omissions.

Ordering remains expense date descending, with document ID descending as a stable tie-breaker (not creation timestamp ordering). Version 2 cursors retain the last **consumed** position of each stream, preserving unconsumed buffered rows. Legacy date/id cursors are accepted. Duplicate documents are owned exclusively by the canonical date stream. A scan-budget page can be empty with a continuation cursor; clients must continue until cursor is null. Concurrent edits that move an expense's date are not a snapshot-isolated listing.

Filtered summary/totalCount retain the existing loaded-page contract; the UI accumulates pages. They are not advertised as full-result totals before all pages are loaded.

## Deployment and backfill

Deploy the additional composite index before the code:

```sh
firebase deploy --only firestore:indexes --project <target-project>
```

Wait until employeeId ASC + expenseDate DESC is ready. The existing employeeId ASC + date DESC index remains required. Owner queries use automatic single-field date indexes; document ID descending follows the final index direction. The old employee missing-index fallback is replaced by these explicitly required indexes; errors surface instead of silently broadening employee reads. No searchTerms composite index is needed by the new scanner.

No backfill is required for discoverability of documents with an ISO `date` or legacy ISO `expenseDate`. No production writes or index deployment were performed. Documents with neither usable date cannot be assigned a correct day from month/year or createdAt and need an audited data repair if present. Existing monthly aggregate correctness is outside this query repair; this change does not rebuild those aggregates.

## Validation

- New regressions: 8 deterministic tests passed; all 9 including the integration test passed with the Firestore emulator. Coverage includes newest unindexed record/₹1532 total, every search field, normalized names/IDs/substrings, combined filters, inclusive date endpoints, conflicting date metadata, legacy records, ties, 137-record pagination, scan-budget continuation, tenant isolation, RBAC, invalid cursors and lifecycle index preservation.
- Focused suite: 26 passed, 0 failed, 4 emulator-gated tests skipped in the non-emulator run. The new integration regression was separately executed against the emulator.
- Broader expense suite: 72 passed, 3 failed, 6 skipped (before adding the separately run emulator test). The same three failures were reproduced from HEAD in an isolated baseline: two expense-update fixtures omit required dates; one mutation test asserts a whitespace-sensitive source regex. They are unchanged by this patch.
- `npm run build -- --webpack`: passed, exit 0, including production route generation.
- `npm run build` (Turbopack): stalled during compile and was interrupted; no successful Turbopack build is claimed.
